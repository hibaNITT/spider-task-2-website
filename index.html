What is this project?

Octo-Shell is a custom shell written entirely in C. Think of it like building your own mini version of bash/zsh from scratch.

  • Level 1: A working shell with builtins (echo, cd, exit) and external command execution
  • Level 2: NITTalk — a custom file transfer protocol with a 72-byte packed header
  • Level 3: Diffie-Hellman key exchange + XOR stream cipher encryption
  • Level 4: Tripwire IDS — a raw socket intrusion detection system

Step 1: Open WSL

Open your terminal and launch Ubuntu:

wsl -d ubuntu

Level 1 — The Core Shell

This is where it all begins. We build a basic REPL (Read-Eval-Print Loop) — the heart of any shell.

How it works

  1. main.c prints the prompt octo-shell$ and reads your input
  2. execute.c tokenizes the input (splits it into words)
  3. If it's a builtin (exit, cd, echo), handle it directly
  4. Otherwise, fork() a child process and use execvp() to run external programs

Key concept: fork() + execvp()

This is the classic Unix pattern for running commands:

pid_t pid = fork();        // Split into parent + child
if (pid == 0) {
    execvp(args[0], args); // Child becomes the command
} else {
    waitpid(pid, NULL, 0); // Parent waits for child
}

The parent process (our shell) creates a clone of itself. The child clone then replaces itself with whatever command you typed. The parent just waits.

Level 2 — NITTalk File Transfer

Now we add nittalk — a custom command inside our shell that can send files over the network using TCP sockets.

The 72-Byte Protocol Header

Since TCP is just a stream of bytes, the receiver needs to know: "what file is coming and how big is it?"

We solve this with a fixed-size header:

Field Size Purpose
Verification 4 bytes "NIT\0" — confirms it's our protocol
Filename 64 bytes Name of the file being sent
Payload Size 4 bytes File size in network byte order
Total 72 bytes

We use __attribute__((packed)) to prevent the compiler from adding hidden padding bytes.

Level 3 — Encryption (Diffie-Hellman + XOR Cipher)

Now we make the file transfer encrypted. Nobody snooping on the network can read the files!

The Math

Problem: How do two computers agree on a secret key without ever sending the key?

Answer: Diffie-Hellman Key Exchange!

Both sides know: p = 9973 (prime), g = 5 (generator)

  1. Each side picks a random private key (a and b) — never shared
  2. Each computes a public key: A = ga mod p, B = gb mod p
  3. They swap public keys over the network
  4. Each computes the shared secret: K = Ba mod p = Ab mod p

Both get the same K, but an attacker who only sees A and B can't figure it out!

Encryption with XOR

The shared secret seeds a Linear Congruential Generator (LCG) that produces a stream of pseudorandom bytes:

next = (1664525 × current + 1013904223) mod 2³²

Each file byte gets XOR'd with a keystream byte:

encrypted = plaintext XOR keystream_byte
decrypted = encrypted XOR keystream_byte  // XOR reverses itself!

  • Both should also print matching Keystream values

Level 4 — Tripwire IDS (Intrusion Detection)

The final boss. We build a raw socket packet sniffer that monitors network traffic and flags unauthorized connections.

How it works

  • Uses SOCK_RAW to capture packets at the IP layer
  • Extracts the source IP from each packet's IP header
  • Compares it against a trusted "teammate" IP
  • Green = authorized traffic, Red = intruder alert!

Compile the tripwire

gcc src/tripwire.c -o src/tripwire
⚠️ Needs sudo! Raw sockets require root privileges.

Sudo stands for "SuperUser DO." It is a command that allows a permitted user to execute a command with the security privileges of another user—specifically, the root (superuser).

We are using sudo because of the socket(AF_INET, SOCK_RAW, IPPROTO_TCP) call. When you use SOCK_RAW, you are telling the kernel: "I want to bypass your standard networking rules and talk directly to the network interface card (NIC) hardware."

Access to Hardware: Raw access is incredibly powerful. A program with raw socket access can sniff private passwords, hijack connections, or spoof identities.

The Restriction: Because this is a massive security risk, the Linux kernel strictly prohibits standard users from opening raw sockets.

Only the root user is trusted with this level of access.

Tripwire Testing Guide with 2 laptops

Scenario Overview

To verify the functionality of the Tripwire module, we will simulate a scenario using two machines on the same local network:

  • Machine A (The Source): Runs the octo-shell and the Tripwire intrusion detection system.
  • Machine B (The Teammate): The authorized machine designated to communicate securely with the source.

Prerequisites

  1. Both machines must be connected to the same Local Area Network (LAN).
  2. Machine A must be running a Linux environment (or WSL) with gcc installed, since raw sockets require POSIX capabilities.
  3. Administrative (root/sudo) privileges are required on Machine A to bind to SOCK_RAW.

Step 1: Network Configuration

Identify the local IP addresses of both machines.

  • Assume Machine A has the IP 192.168.1.10.
  • Assume Machine B has the IP 192.168.1.15.

Step 2: Configure the Trusted Teammate

  1. On Machine A, open the source code file src/tripwire.c.
  2. Locate the #define directive for the teammate's IP address.
  3. Update the value to match the IP address of Machine B:
#define TEAMMATE_IP "192.168.1.15"

Save the file.

Step 3: Compilation and Execution

cd src
gcc tripwire.c -o tripwire
sudo ./tripwire

Expected Output:

Tripwire Active. Monitoring traffic...

Step 4: Simulating Authorized Traffic (Teammate)

  1. On Machine B, send a request to Machine A:
curl http://192.168.1.10

Verification: On Machine A’s terminal, Tripwire should output:

[*] Authorized traffic from: 192.168.1.15

Step 5: Simulating Unauthorized Traffic (Intruder)

  1. From an unauthorized device (e.g., IP 192.168.1.50):
curl http://192.168.1.10

Verification: On Machine A’s terminal, Tripwire should output:

[!] ALERT: Intruder detected! Source: 192.168.1.50

If you see Green for the teammate and Red for the intruder, your Tripwire IDS is working correctly.

Problem Encountered

Laptop B was unable to ping Laptop A or communicate with the WSL instance.

Symptoms

  • ping 192.168.1.39 → Request timed out.
  • Test-NetConnection → Ping failed.
  • WSL IP (172.17.66.30) was visible, but communication from another laptop was not possible.

Step 1: Verify WSL IP

ip a
hostname -I

Result: WSL IP = 172.17.66.30

Step 2: Verify Windows Wi-Fi IP

ipconfig

Result: Wi-Fi IP = 192.168.1.39

Step 3: Test Network Connectivity

ping 192.168.1.39

Result: Request timed out → Problem lies with Windows networking, not WSL.

Step 4: Check Network Profile

Get-NetConnectionProfile

Result: NetworkCategory : Public

A Public network blocks many incoming connections by default.

Step 5: Change Network to Private

Set-NetConnectionProfile -InterfaceAlias "Wi-Fi" -NetworkCategory Private
Get-NetConnectionProfile

Result: NetworkCategory : Private

Step 6: Enable Ping Through Firewall

Enable-NetFirewallRule -Name FPS-ICMP4-ERQ-In

This allows incoming ICMP (ping) requests.

Step 7: Test Again

ping 192.168.1.39

Result: Reply from 192.168.1.39 → Communication successful.

Root Cause

The Windows Wi-Fi network was configured as Public, causing Windows Firewall to block incoming ICMP and network traffic. Since Laptop B could not reach Windows on Laptop A, the issue was unrelated to WSL.

Solution Summary

  1. Verified WSL IP using ip a.
  2. Verified Windows Wi-Fi IP using ipconfig.
  3. Tested connectivity using ping.
  4. Checked network profile using Get-NetConnectionProfile.
  5. Changed the network from Public to Private.
  6. Enabled Windows Firewall ICMP rule (Enable-NetFirewallRule -Name FPS-ICMP4-ERQ-In).
  7. Confirmed successful communication by pinging Laptop A from Laptop B.
